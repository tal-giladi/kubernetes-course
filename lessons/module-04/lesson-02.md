# 12 - Volumes, PersistentVolumes, PVCs and StorageClasses

A container's filesystem dies with the container. A **volume** is storage attached to a
Pod; how long it lives depends entirely on which kind you pick.

## The ephemeral ones

  - **`emptyDir: {}`** - a scratch directory created when the Pod is scheduled and deleted
    when the Pod is deleted. Survives a *container* restart, not a Pod deletion. Shared by
    every container in the Pod - which is what made the init container in lesson 03 work.
    `emptyDir: {medium: Memory}` puts it in tmpfs (fast, counts against the Pod's memory
    limit).
  - **`configMap` / `secret` / `downwardAPI` / `projected`** - read-only, generated by the
    kubelet. Lesson 11.
  - **`hostPath`** - a path on the node. Occasionally right for node agents (a DaemonSet
    reading `/var/log`), and a security hole in every other case: `hostPath: /` gives the
    container the node. Pod Security Admission blocks it in `restricted` mode.

`downwardAPI` deserves a mention: it exposes the Pod's own metadata (name, namespace,
labels, resource limits) as files or env vars. It is how an app learns its own Pod name
without guessing at `hostname`.

## The persistent ones, and the split that makes them work

    PersistentVolumeClaim   "I need 5Gi, ReadWriteOnce"     <- the app team's ask, namespaced
    PersistentVolume        an actual disk                  <- cluster-scoped, real storage
    StorageClass            "how to make one of those"      <- the recipe, cluster-scoped

The point of the split is that a Deployment never mentions a disk. It mentions a *claim*,
and the same YAML works on your laptop, on AKS with Azure Disk, and on EKS with EBS -
because the StorageClass differs, not the workload.

**Dynamic provisioning** is the normal path: you create a PVC naming a StorageClass, a CSI
driver creates real storage and a matching PV, and the two are **bound**. Static
provisioning (an admin pre-creates PVs) still exists for pre-existing NFS exports and the
like.

Your kind cluster ships `local-path` as the default StorageClass - it provisions a
directory on a node.

    kubectl get storageclass
    kubectl get pv
    kubectl -n lesson-12 get pvc

## Access modes are about *nodes*, not Pods

  - **ReadWriteOnce (RWO)** - mountable read-write by Pods on **one node**. Almost every
    block device: EBS, Azure Disk, local-path.
  - **ReadOnlyMany (ROX)**, **ReadWriteMany (RWX)** - many nodes. RWX needs a file-based
    backend: NFS, Azure Files, CephFS, EFS.
  - **ReadWriteOncePod** - exactly one Pod, cluster-wide. The real mutual-exclusion
    primitive when you need it.

This is the trap behind "my second replica is stuck in `ContainerCreating`": a Deployment
with 2 replicas and one RWO PVC. Both Pods want the same disk; if they land on different
nodes the second one waits forever. **Deployments with a PVC are effectively
single-replica** unless the storage is RWX. When each replica needs its own disk, you want
a StatefulSet (lesson 13).

## volumeBindingMode: why your PVC is "Pending" and that is fine

    kubectl get sc standard -o jsonpath='{.volumeBindingMode}'
    WaitForFirstConsumer

With `Immediate`, storage is created as soon as the PVC exists - and may be created in a
zone where your Pod cannot run. With `WaitForFirstConsumer` (the sane default, and what
kind uses), the PVC deliberately stays `Pending` until a Pod that uses it is scheduled, so
the disk is created in the right place. A `Pending` PVC with no Pod is **not** an error.

## Reclaim policy: how you lose data

    persistentVolumeReclaimPolicy: Delete   # default for dynamic provisioning
                                   Retain   # keep the PV and the data after the PVC goes

With `Delete`, deleting the PVC deletes the real disk. `kubectl delete ns` on a namespace
with a database in it is therefore final. For anything you care about, use a StorageClass
with `Retain`, and know that the released PV must then be cleaned up by hand before it can
be reused.

Deleting a PVC that a Pod is still using does not take effect immediately, either -
finalizers hold it until the last consumer goes away. A PVC stuck in `Terminating` is
almost always a Pod you forgot about.

## Expanding

If the StorageClass has `allowVolumeExpansion: true`, editing the PVC's
`spec.resources.requests.storage` upward grows it (some drivers need a Pod restart).
Shrinking is never supported.

## Do this

In namespace `lesson-12`, with the `hello:1.1.0` image:

1. Look at what the cluster offers:

       kubectl get storageclass
       kubectl get sc standard -o yaml | grep -E 'provisioner|reclaimPolicy|volumeBindingMode'

2. Create a PVC `data`: 1Gi, `ReadWriteOnce`, default StorageClass. Check it immediately:

       kubectl -n lesson-12 get pvc

   It is `Pending`. That is `WaitForFirstConsumer`, not a failure.

3. Create a Deployment `writer`: **1** replica, label `app=writer`, container `hello`,
   port 8080, env `DATA_DIR=/data`, with the PVC mounted at `/data`. The PVC should bind
   within seconds of the Pod being scheduled:

       kubectl -n lesson-12 get pvc,pv

4. Write, then destroy, then read:

       kubectl -n lesson-12 exec deploy/writer -- wget -qO- http://127.0.0.1:8080/data
       kubectl -n lesson-12 exec deploy/writer -- wget -qO- http://127.0.0.1:8080/data
       kubectl -n lesson-12 delete pod -l app=writer
       kubectl -n lesson-12 rollout status deploy/writer
       kubectl -n lesson-12 exec deploy/writer -- wget -qO- http://127.0.0.1:8080/data

   The last call returns the earlier lines - written by a Pod that no longer exists - plus
   a new one from the new Pod. That is persistence.

5. Now the contrast. A second Deployment `scratch`, same image and env, but `/data` backed
   by `emptyDir: {}`. Write to it, delete its Pod, read again: the file is empty. Same
   YAML shape, completely different guarantee.

6. Feel the RWO limit:

       kubectl -n lesson-12 scale deploy/writer --replicas=3
       kubectl -n lesson-12 get pods -o wide

   Extra replicas that land on the writer's node start fine (same node, RWO is satisfied);
   any that the scheduler places elsewhere sit in `Pending`/`ContainerCreating`. Read the
   reason yourself, then scale back to 1:

       kubectl -n lesson-12 describe pod <a stuck one> | tail -15
       kubectl -n lesson-12 scale deploy/writer --replicas=1

## Hints

- `kubectl -n lesson-12 create -f -` with a PVC manifest; there is no `kubectl create pvc`.
- The Pod side is two pieces: a `volumes:` entry with
  `persistentVolumeClaim: {claimName: data}`, and a `volumeMounts:` entry.
- The `hello` image runs as uid 1654 and its Dockerfile already `chown`s `/data`; the
  local-path provisioner creates directories world-writable, so no `fsGroup` is needed
  here. On a real cluster you often do need `securityContext.fsGroup` to make a mounted
  volume writable by a non-root process - remember that when it bites you.
- `kubectl -n lesson-12 get events --sort-by=.lastTimestamp` explains a stuck PVC faster
  than anything else.
